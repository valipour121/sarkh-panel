# sarkh panel

پنل دسکتاپ (Tkinter) برای **ارسال هم‌زمان و زمان‌بندی‌شده‌ی سفارش از چند حساب کارگزاری**.
برنامه درخواست سفارشی را که یک‌بار از مرورگر گرفته‌ای (`Copy as cURL`) برای هر حساب نگه می‌دارد و
در لحظه‌ی دقیق تعیین‌شده، چند بار پشت‌سرهم و با فاصله‌ی مشخص دوباره ارسال می‌کند؛ بعد پاسخ‌ها را
ثبت و تحلیل می‌کند تا بفهمی کدام درخواست ثبت شد، کدام رد شد و چرا.

> آخرین نسخه: **`sarkh_panel_v15.py`** (فایل‌های دیگر نسخه‌های قبلی‌اند).
> ⚠️ ارسال‌ها **سفارش واقعی** هستند.

---

## ۱. اجرا

پیش‌نیاز: Python 3 با `tkinter` (در نصب‌کننده‌ی python.org گزینه‌ی *tcl/tk* باشد) و `requests`.

```
pip install requests
python sarkh_panel_v15.py
```

اجرا با دابل‌کلیک روی ویندوز ممکن است خطا را نشان ندهد؛ فایل `run.bat` کنار برنامه بساز:

```
@echo off
cd /d "%~dp0"
python sarkh_panel_v15.py
pause
```

## ۲. جریان کار

1. تو مرورگر (DevTools ← Network) یک سفارش واقعی بفرست و درخواست **POST** سفارش را `Copy as cURL (bash)` کن.
   (درخواست‌های هم‌نامِ `GET` تنظیمات فرم‌اند، نه ثبت سفارش.)
2. **افزودن حساب**: نام، کارگزاری و curl را بگذار (دکمه‌های «پیست» و «پاک کردن» بالای پنجره‌اند).
3. در جدول اصلی برای هر حساب **وقفه / تریگر / تعداد** را تنظیم کن (با یک کلیک روی خانه؛ Enter ثبت، Esc انصراف).
4. **ساعت پایه** را بگذار و «شروع» بزن؛ یا با «ارسال تست» فوری امتحان کن.
5. نتیجه را در «مشاهده لاگ» هر حساب ببین؛ برای عیب‌یابی «لاگ کل پنل» را کپی/ذخیره کن.

## ۳. منطق زمان‌بندی

هر حساب برنامه‌ی خودش را از چند عدد می‌سازد (`compute_schedule`):

| مقدار | معنی |
|---|---|
| **ساعت پایه** (مشترک) | مثلاً `08:44:50` |
| **تریگر** (ms) | زمان درخواست *وسط*: `پایه + تریگر` ← با تریگر `9800` می‌شود `08:44:59.800` |
| **تعداد** | کل درخواست‌ها |
| **وقفه** (ms) | فاصله‌ی دو درخواست؛ **حداقل ۳۰۰** (کمتر خودکار ۳۰۰ می‌شود) |

درخواست تریگر دقیقاً روی زمان تریگر می‌نشیند؛ `(تعداد−۱) // ۲` درخواست قبل از آن و بقیه بعد از آن:

```
تعداد ۵، وقفه ۳۲۰، تریگر 08:44:59.800
  .160   .480   [.800 تریگر]   00.120   00.440
  ←۲ قبل→                      ←۲ بعد→
تعداد ۸: ۳ قبل + تریگر + ۴ بعد
```

- هر حساب = یک ریسمان کارگر (`OrderWorker`)؛ همه از یک ساعتِ پایه‌ی مشترک می‌گیرند، پس هم‌زمان‌اند.
- اگر **کل** برنامه‌ی یک حساب گذشته باشد، «شروع» اجرا نمی‌شود. اگر فقط اولین درخواست گذشته باشد، با تأیید تو فوری شروع می‌شود.
- «ارسال تست»: همین الان، با تعداد/فاصله‌ی بخش تست، برای همه‌ی حساب‌های فعال.
- ساعت کامپیوتر باید دقیق باشد (`w32tm /resync`). جابه‌جایی ساعت ویندوز وسط اجرا همه‌ی ارسال‌ها را هم‌زمان جلو یا عقب می‌برد.
- اگر بیش از یک حساب فعال باشد، «گزارش زنده» خط به خطِ درخواست‌ها را نمی‌نویسد (ترتیب پاسخ‌ها به هم می‌ریزد)؛ جزئیات در لاگ هر حساب هست.

## ۴. موتور ارسال

**کارگزاران عمومی** (سامان، پاسارگاد، کاریزما، اکسیر، مفید): هر درخواست در زمان مطلق خودش (`شروع + k×وقفه`)
در یک ریسمان جدا شلیک می‌شود و **منتظر پاسخ درخواست قبلی نمی‌ماند**. بدنه‌ی curl عیناً ارسال می‌شود.

**نهایت‌نگر** (تیکت): هر سفارش یک `orderTicket / ticketGeneration` یک‌بارمصرف دارد که با هر سفارشِ پردازش‌شده
(حتی ردشده) عوض می‌شود و پاسخ ردشده همیشه تیکت تازه را نمی‌دهد. پس ارسال‌ها **زنجیره‌ای** است:

- تیکت اولیه با `GET …/orderTicket` گرفته می‌شود؛ از ۳ ثانیه قبل از شروع، هر ۰.۳ ثانیه تازه می‌شود.
- شلیک بعدی وقتی می‌رود که **هم** ≥ وقفه از قبلی گذشته **هم** تیکت تازه (generation بزرگ‌تر) رسیده باشد.
  بعد از هر ارسال، هر ۸۰ms یک GET تیکت می‌رود. اگر تا ۲۵۰ms بعد از زمان مجاز نرسید، با آخرین تیکت می‌رود.
- تیکتِ پاسخ‌ها (موفق یا خطای تیکت‌کهنه) هم برای شلیک بعدی استفاده می‌شود.
- با «توقف بعد از ثبت»، شلیک بعدی منتظر پاسخ قبلی هم می‌ماند تا سفارش اضافه در راه نباشد.

**توقف:** «توقف بعد از ثبت» (حساب پس از اولین ثبت موفق متوقف می‌شود)، «کد پاسخ توقف» (متنی که اگر در پاسخ بود متوقف شود)، دکمه‌ی توقف.
«ثبت موفق» در نهایت‌نگر: HTTP 2xx + وجود `orderTicket` در پاسخ؛ در بقیه: HTTP 2xx بدون کد خطا (حدس عمومی).

## ۵. اتصال گرم (Warm connections)

بدون آن، هر درخواست DNS + TCP + TLS تازه می‌ساخت **بعد از** ثبت ساعت ارسال، و رسیدن به کارگزار ده‌ها تا صدها ms دیرتر و ناهمگون می‌شد.

- DNS یک‌بار حل می‌شود (IP نگه داشته می‌شود؛ SNI و گواهی با نام اصلی بررسی می‌شود) و یک SSL context مشترک است.
- هر شلیک یک **اتصال اختصاصی از‌قبل‌آماده** می‌گیرد. اتصال دو شلیک اول، ۳ ثانیه قبل از شروع باز می‌شود؛ بعد از هر شلیک، اتصال شلیک‌های بعدی همان لحظه باز می‌شود.
- **پیش‌گرمی**: خودکار = `max(300, ۲×زمان دست‌دادنِ اندازه‌گیری‌شده + ۵۰)` ms؛ یا دستی (حداقل ۳۰۰).
- شروع دست‌دادن حساب‌ها ۰ تا ۶۰ms (بر اساس شناسه‌ی حساب) از هم فاصله می‌گیرد تا ۲۰ حساب با هم صف نکشند.
- اگر اتصال به‌موقع آماده نبود یا قطع شده بود، شلیک منتظر نمی‌ماند و روی اتصال تازه می‌رود؛ در لاگ «⚠ اتصال سرد» می‌خورد.
- بدنه، هدرها، کوکی و پارامترها عین `requests` ساخته می‌شوند (`Accept-Encoding` روی `gzip, deflate` ثابت است؛ ریدایرکت دنبال نمی‌شود).
- با پروکسی سیستم/محیط، آدرس غیر HTTP(S) یا خاموش‌کردن تیک «اتصال گرم»، ارسال با `requests` انجام می‌شود.

```
بدون گرم:  [ثبت ساعت] → DNS → TCP → TLS → ارسال بایت‌ها
گرم:       (چند صد ms قبل: DNS/TCP/TLS)      [ثبت ساعت] → ارسال بایت‌ها
```

## ۶. دیباگ بای والیوم (پیش‌فرض روشن)

گاهی از پاسخ کارگزار نمی‌شود فهمید کدام درخواست ثبت شد. پس درخواست k از N، حجم **`پایه − (N−k)`** را می‌فرستد و آخری حجم کامل را؛
مثلاً حجم ۶۲۰ و ۵ درخواست: `616, 617, 618, 619, 620`. حجم سفارشِ ثبت‌شده در لیست سفارش‌های کارگزار می‌گوید کدام درخواست بوده.

- فیلد حجم خودکار پیدا می‌شود (`quantity, qty, volume, orderVolume, …`، حتی تودرتو یا رشته‌ی عددی) یا در «فیلد(های) حجم» با کاما نوشته می‌شود. بدنه‌ی فرمی (`a=1&volume=620`) هم پشتیبانی می‌شود.
- نهایت‌نگر: `volume` و `diffVolume` عوض می‌شوند و `grandTotal` متناسب می‌شود.
- اگر فیلدی پیدا نشود یا حجم پایه از تعداد درخواست‌ها کمتر باشد، هشدار می‌دهد و بدنه عیناً می‌رود (حجم صفر/منفی نمی‌رود).
- چون درخواست‌های قبل از آخری حجم کمتری دارند، اگر چند تا موفق شوند مجموعشان ثبت می‌شود؛ «توقف بعد از ثبت» را هم روشن کن.

## ۷. لاگ‌ها

برای هر درخواست یک رکورد: ردیف/شماره، حجم، ساعت ارسال و دریافت، HTTP، **نتیجه / کد خطا** و جزئیات کامل.

- ستون نتیجه: نهایت‌نگر `✔ ثبت شد` یا کد خطای داخل متن (مثلاً `1032` = بازار بسته)؛ بقیه کد خطا (در صورت وجود).
- جزئیات: خلاصه، نوع اتصال (گرم/سرد)، زمان‌ها، تیکت ارسالی/دریافتی، درخواست ارسال‌شده (متد، آدرس، بدنه — **بدون هدر و کوکی**)، پاسخ خوانا و پاسخ خام.
- **لاگ بافر‌شده** (پیش‌فرض روشن): وسط ارسال فقط پاسخ خام ذخیره می‌شود؛ خلاصه‌سازی و نوشتن در جدول بعد از پایان ارسال‌ها انجام می‌شود (جدول تا پایان بازه خالی است).
- **گزارش زنده**: چک‌باکس، پیش‌فرض خاموش؛ خطوط پشت‌صحنه نگه داشته می‌شود (۳۰۰۰ خط آخر) و با روشن‌کردن ظاهر می‌شود.
- در طول اجرا GC پایتون خاموش است (نویز زمان‌بندی و فراخوانی بین‌ریسمانی Tk را کم می‌کند).

### ماندگاری و تاریخچه
- با بستن و باز کردن پنل، **آخرین لاگ هر حساب** (تا ۳۰۰ درخواست)، گزارش زنده و تنظیمات پنل برمی‌گردد. فقط لاگ حسابی که **درخواست جدید** می‌فرستد جایگزین می‌شود.
- **💾 ذخیره‌ی حالت پنل**: با تاریخ شمسی و نام؛ تنظیمات همه‌ی حساب‌ها + لاگ‌ها. **🗂 تاریخچه‌ی لاگ**: انتخاب یک حالت آن را بالا می‌آورد (وضعیت فعلی قبلش خودکار ذخیره می‌شود).
- **📋 لاگ کل پنل**: لاگ همه‌ی کارگزاری‌ها در یک متن واحد (مشخصات، خلاصه‌ی حساب‌ها، جدول زمانیِ ادغام‌شده، گزارش زنده، جزئیات) برای عیب‌یابی؛ **بدون curl/کوکی/توکن**. کپی یا ذخیره در فایل.

## ۸. ردیف و پیش‌فرض‌ها

هر حساب یک **شماره‌ی ردیف** دارد (۱ تا آخر؛ با جابه‌جایی ردیف‌ها تغییر می‌کند). برای **حساب جدید**:

| مقدار | پیش‌فرض |
|---|---|
| وقفه | `600 + 10×ردیف` (ردیف ۱ ← ۶۱۰، ردیف ۱۰ ← ۷۰۰) |
| پیش‌گرمی | `400 + 10×ردیف` (ردیف ۱ ← ۴۱۰) |
| تریگر / تعداد | `9800` / `5` |
| دیباگ بای والیوم، اتصال گرم، لاگ بافر‌شده | روشن |
| توقف بعد از ثبت | خاموش |

دکمه‌ی **🔢 اعمال پیش‌فرض ردیفی** همین مقادیر را (وقفه، پیش‌گرمی، دیباگ بای والیوم، اتصال گرم) روی همه‌ی حساب‌های موجود می‌گذارد.
در اولین اجرای v15، دیباگ بای والیوم یک‌بار برای همه‌ی حساب‌ها روشن می‌شود (بعدش خاموش‌کردنِ دستی حفظ می‌شود).

## ۹. کارگزاران

| کارگزار | رفتار |
|---|---|
| سامان، پاسارگاد، کاریزما، اکسیر، مفید | عمومی: بدنه‌ی curl عیناً؛ موفق = HTTP 2xx بدون کد خطا |
| نهایت نگر | تیکت یک‌بارمصرف + ارسال زنجیره‌ای + ستون نتیجه‌ی اختصاصی + حجم/`grandTotal` در دیباگ |

افزودن کارگزار تازه: یک مدخل در دیکشنری `BROKERS` (برچسب، parser، و در صورت نیاز `summary` / `is_success`).

## ۱۲. عیب‌یابی سریع

| نشانه | معنی |
|---|---|
| HTTP 400 `Invalid parameter` + `orderTicket` در پاسخ (نهایت‌نگر) | تیکت کهنه فرستاده شده؛ پاسخ، تیکت درست را می‌دهد |
| کد `1032` (نهایت‌نگر) | بازار بسته است (درخواست تا بررسی بازار رسیده) |
| خطای `[1005]` حداقل فاصله‌ی دو سفارش ۳۰۰ms (در اکسیر دیده شده) | ظاهراً فاصله سمت سرور سنجیده می‌شود، نه ساعت ارسال تو |
| پاسخ شبیه تنظیمات فرم (`allowed…Types`) | curl یک درخواست `GET` گرفته‌ای، نه `POST` سفارش |
| 401 / 403 | توکن ورود منقضی شده؛ curl تازه بگیر |
| «⚠ اتصال سرد» | اتصال به‌موقع آماده نبود؛ پیش‌گرمی را بیشتر کن |
| تفاوت ثابت ساعت ارسال با برنامه | جابه‌جایی ساعت ویندوز؛ ساعت را همگام کن |

## ۱۳. وضعیت آزمون و محدودیت‌ها

- منطق‌ها (زمان‌بندی، زنجیره‌ی تیکت، اتصال گرم، دیباگ حجم، لاگ، ذخیره/تاریخچه، پنجره‌ها) روی سرورهای شبیه‌سازی‌شده و پنجره‌ی واقعی تست شده‌اند. نهایت‌نگر با نسخه‌های قبلی روی کارگزار واقعی هم دیده شده؛ **اتصال گرم و قابلیت‌های جدیدتر روی کارگزار واقعی تست نشده‌اند** (مثلاً محدودیت تعداد اتصال هم‌زمان یا زمان بستن اتصال بی‌کار کارگزارها ناشناخته است).
- جبران RTT، انتظار فعال برای دقت میلی‌ثانیه، ارسال از یک ریسمان و تشخیص جابه‌جایی ساعت ویندوز هنوز پیاده نشده‌اند.
- «موفق» برای کارگزاران عمومی حدسی است (HTTP 2xx بدون کد خطا)؛ نمونه‌ی پاسخ موفق هر کارگزار می‌تواند دقیقش کند.

## ۱۴. تاریخچه‌ی نسخه‌ها

`v2` پنل چندحسابی، تست، زمان‌بندی میلی‌ثانیه‌ای · `v3` بررسی گذشته‌بودن زمان · `v4` نهایت‌نگر و تیکت ·
`v7` زنجیره‌ی تیکت، ستون نتیجه، حداقل ۳۰۰ms، توقف بعد از ثبت · `v8` جزئیات کامل و لاگ بافر‌شده ·
`v9` زمان‌بندی تریگری و ویرایش درجا · `v11` گزارش زنده‌ی اختیاری، ماندگاری، تاریخچه‌ی شمسی، دیباگ بای والیوم ·
`v12` مفید · `v13` دیباگ پیش‌فرض روشن · `v14` اتصال گرم · `v15` لاگ کل پنل، پیست/پاک‌کردن curl، ردیف و پیش‌فرض ردیفی.
(`v10` و `v14` فایل جدا در ریپو ندارند و در نسخه‌های بعدی هستند.)
