# sarkh_engine — موتور ارسال C++ (پورت ورژن ۱۵ پنل)

موتورِ **بدون رابط** برای سرور لینوکس. همان `accounts.json` پنل پایتون را می‌خواند؛
پنل پایتون روی کامپیوتر خودتان برای مدیریت حساب‌ها (چسباندن curl، وقفه/تریگر/تعداد) می‌ماند
و فایل `accounts.json` را روی سرور کپی می‌کنید (**حاوی کوکی/توکن است:** `chmod 600`).

## شروع سریع (روی سرور اوبونتو)
    git clone https://github.com/valipour121/sarkh-panel.git && cd sarkh-panel/v16_cpp
    sudo ./tune_server.sh        # نصب ابزارها + chrony + منطقه‌ی زمانی تهران
    make
    # accounts.json را از پنل پایتون (کامپیوتر خودتان) با scp روی سرور بگذارید؛ chmod 600 accounts.json
    chronyc tracking             # ساعت سرور باید با خطای ~1ms یا کمتر سینک باشد
    ./sarkh_engine probe --accounts accounts.json
    ./sarkh_engine dry   --accounts accounts.json --base 08:44:50     # برنامه‌ی زمانی را وارسی کنید
    ./sarkh_engine test  --accounts accounts.json --count 1 --interval 340   # یک ارسال کوچک (واقعی!)
    ./run_market.sh              # روز بازار، چند دقیقه قبل از شروع؛ هسته‌های داخل فایل را با nproc سرور هماهنگ کنید

## ساخت
    sudo apt install g++ make libssl-dev zlib1g-dev
    make                      # خروجی: ./sarkh_engine

## دستورها
    ./sarkh_engine dry   --accounts accounts.json --base 08:44:50   # فقط برنامه‌ی زمانی (چیزی نمی‌فرستد)
    ./sarkh_engine probe --accounts accounts.json --n 10            # تأخیر DNS/TCP/TLS تا هر کارگزار (چیزی نمی‌فرستد)
    ./sarkh_engine test  --accounts accounts.json --count 5 --interval 340   # ارسال فوری (مثل «ارسال تست» پنل)
    ./sarkh_engine run   --accounts accounts.json --base 08:44:50   # ارسال زمان‌بندی‌شده‌ی تریگری

⚠ `test` و `run` **درخواست واقعی** به کارگزار می‌فرستند (مثل پنل).
ساعت پایه به **وقت محلی سرور** است: `TZ=Asia/Tehran ./sarkh_engine run ...`

منطق تریگر دقیقاً مثل پنل: تریگر ۹۸۰۰ با پایه‌ی ۰۸:۴۴:۵۰ ⇒ ۰۸:۴۴:۵۹.۸۰۰؛ درخواست وسط روی تریگر،
`(تعداد-۱)//۲` درخواست قبل از آن؛ حداقل وقفه ۳۰۰ms.

## گزینه‌های عملکرد
| گزینه | کار |
|---|---|
| `--send-cpus 2,3,4,5` | ریسمان‌های ارسال، هرکدام روی یک هسته (تعداد ریسمان = تعداد هسته‌ها) |
| `--conn-cpus 6,7` / `--read-cpus 1` | ریسمان‌های اتصال‌ساز / خواننده‌ی پاسخ |
| `--rt` | اولویت SCHED_FIFO برای ریسمان‌های ارسال (نیاز به root) |
| `--spin-us 2000` | چند میکروثانیه‌ی آخرِ پیش از شلیک با انتظار فعال (spin) |
| `--only a,b` / `--live` / `--force` | فیلتر حساب‌ها / چاپ زنده‌ی هر پاسخ / ادامه با وجود زمان گذشته |
| `--cafile F` / `--insecure` | CA سفارشی (برای تست) / بدون بررسی گواهی (فقط تست) |

## خروجی
در `engine_out/`: `run_*.txt` (خوانا) و `run_*.jsonl` (هر درخواست یک خط، با پاسخ کامل و بدنه‌ی ارسالی).
مهم‌ترین عدد: **`late_us`** = فاصله‌ی «لحظه‌ی برنامه‌ریزی‌شده» تا «لحظه‌ی نوشتن روی سوکت» (تأخیر خودِ موتور).
زمان رسیدن به کارگزار = `late_us` + تأخیر شبکه؛ این‌ها فقط سمتِ خودِ سرور شما را اندازه می‌گیرند.

## چه چیزی پورت شد و چه چیزی نه
پورت‌شده: پارس curl، زمان‌بندی تریگری، اتصال گرم (هر شلیک یک اتصال TLS از‌قبل‌آماده)، زنجیره‌ی تیکت نهایت‌نگر،
دیباگ بای والیوم (JSON و فرم)، توقف بعد از ثبت / روی متن، خلاصه‌ی نتیجه‌ی هر کارگزار، gzip/chunked.
پورت‌نشده: رابط گرافیکی، پنجره‌ی لاگ، تاریخچه/تاریخ شمسی، ورودیِ «کد پایتونِ مبدل curl» (فقط curl خام).
تفاوت: لاگ‌ها در حافظه نگه داشته و **بعد از پایان** نوشته می‌شوند (مثل گزینه‌ی «لاگ بافرشده»).

## پیش از استفاده‌ی واقعی
1. `tune_server.sh` و `chronyc tracking` (ساعت سرور باید با خطای حدود ۱ms یا کمتر سینک باشد).
2. `probe` برای سنجش تأخیر شبکه تا هر کارگزار.
3. یک `test` کوچک و بی‌خطر؛ مطمئن شوید پاسخ‌ها مثل پنل پایتون است (اثر انگشت TLS و ترتیب هدرها با پایتون فرق دارد).
4. مقادیر `late_us` را روی **همین سرور** و با **همین تعداد حساب** ببینید.
